Create a new public page for **GetStack** at:

`https://gtstk.dev/stats`

The page is called **GetStack Stats** and should serve as the public-facing hub for aggregate technology intelligence gathered from websites analyzed by GetStack.

## Core idea

GetStack already scans websites to identify CMS platforms, themes, plugins, apps, frameworks, analytics tools, hosting technologies, and other detectable components.

The `/stats` page should turn that accumulated scan data into useful public intelligence.

Think:

**Wappalyzer/BuiltWith-level data presented with the simplicity and polish of a modern SaaS product.**

This should NOT feel like an admin dashboard.

It should feel like a clean, editorial, public-facing **State of the Web Stack** report that happens to be powered by live GetStack data.

Match the existing GetStack visual identity, typography, spacing, navigation, buttons, cards, colors, border radii, and footer. Do not redesign the overall GetStack brand.

# 9. METHODOLOGY / DATA EXPLANATION

This is important.

Heading:

**About the data**

Short, readable explanation:

`GetStack statistics are based on websites submitted for analysis through GetStack. They represent the websites our users investigate, not a random sample of the entire internet. Technologies are identified using publicly detectable signals and may not always be visible or identifiable.`

Include a link:

`Learn how GetStack detects technologies →`

which may point to `/faq` or a future `/methodology` page.

Include key caveats:

* statistics reflect GetStack scans, not the entire web
* individual websites should only count once within an appropriate reporting period if needed to prevent repeated scans distorting results
* detection is based on publicly observable technology
* hidden/server-side technologies may not be detectable
* detection confidence can vary

Keep this visually understated.

# DATA ARCHITECTURE

Build this page so it can consume real aggregate GetStack scan data.

Suggested normalized concepts:

* total_scans
* unique_domains
* detected_technologies
* technology_category
* technology_name
* detection_count
* detection_share
* cms
* theme
* plugin
* app
* framework
* first_seen
* last_seen
* reporting_period

Avoid letting repeated scans of one popular domain artificially dominate public statistics.

Prefer unique-domain aggregation for percentage/share calculations.

For example:

`Sites using Elementor / unique WordPress sites analyzed`

rather than:

`Number of Elementor detections / total scan events`

Where possible, expose the methodology transparently.

# DESIGN DIRECTION

The visual treatment should be:

* clean
* modern
* intelligent
* restrained
* data-forward
* spacious
* premium SaaS
* highly legible

Avoid:

* crypto-dashboard aesthetics
* excessive gradients
* neon visualization
* dozens of tiny widgets
* generic Bootstrap dashboard appearance
* fake real-time indicators
* enormous enterprise tables
* visual clutter

Use subtle borders, cards, typography hierarchy and whitespace.

Charts should feel editorial rather than financial-terminal-like.

Think:

**“State of the Web report” rather than “Google Analytics clone.”**

---

# MOST IMPORTANT PRODUCT IDEA

The page should communicate that GetStack's scanner creates a growing proprietary view of the technologies people are encountering on the web.

The product loop is:

`Website scans`
→ `technology detections`
→ `aggregate statistics`
→ `public insights`
→ `organic discovery`
→ `more website scans`

This is therefore not merely a stats page.

It is the beginning of **GetStack Intelligence**.

Build the architecture so `/stats` can grow into a substantial public data product without needing to rebuild the page later.
